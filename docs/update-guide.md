# 写真の更新ガイド

月1回程度、Codexへ写真の差し替え・並べ替えを依頼します。ローカル検査とブラウザ確認後、公開リポジトリ`bon214/hibi-portfolio`の`main`へpushし、GitHub Pagesのデプロイと公開ファイルを確認します。公開先URLは [https://bon214.github.io/hibi-portfolio/](https://bon214.github.io/hibi-portfolio/) です。

## 1. 更新依頼で渡すもの

- 追加・差し替えするWeb掲載用の画像。
- どの写真を残す・外す・差し替えるか。
- カラー／モノクロのどちらに掲載するか。現在は各20点です。
- 希望する掲載順。ファイル名または既存の固定IDで指定します。編集に任せる場合はその旨を伝えます。
- Instagramから選ぶ場合は、対象アカウントと投稿URL。告知画像と写真を区別します。
- 代替テキストに必要な、写真に写っている内容。
- 掲載する場合のみ、本人が確認したタイトル・撮影情報・短い言葉。

正式な作品名がない写真に作品名を作る必要はありません。代替テキストは画面を見ることが難しい人へ内容を伝えるための文章であり、作者の意図や写る人物の事情を推測する解説にはしません。

依頼例：

> カラーの3点を添付の写真A・B・Cへ差し替え、合計20点を維持してください。先頭作品は現在のまま、A・B・Cをその次に並べます。モノクロの作品と順序は変えません。作品名と撮影地は掲載しません。まずローカルのプレビューで確認します。

## 2. 画像を準備する

1. ユーザーから指定された掲載範囲・作品・順序を確認します。各写真について別途本人承認を得たかどうかと、ユーザーによる公開選定指示を混同しません。今回の40点の掲載順は、ユーザーから編集を任されています。
2. 原寸画像は提供されたフォルダにそのまま残し、公開リポジトリへコピーしません。`color/`・`monochrome/`の各20点について、元ファイルのSHA-256を算出します。
3. Git管理対象外の`artifacts/provided-selection.json`へ、各項目が`id`・`collection`・`file`・`sha256`・`alt`を持つ配列を用意します。`collection`は`color`または`mono`、`file`はそれぞれ`color/元ファイル名.jpg`または`monochrome/元ファイル名.jpg`です。SHA-256は64桁の小文字16進数で記録します。絶対パス、上位フォルダへの参照、重複した元画像は指定しません。
4. `assets/photos/provided/`へWebP閲覧コピーとサムネイルを生成します。長辺400・800・1400・2200pxを候補とし、原寸の長辺で止めます。必要なEXIFの表示方向補正以外に回転を加えず、拡大生成・切り取り・色調変更を行いません。作者の白枠や署名がある場合も保ちます。
5. 書き出した画像そのものの幅・高さを`width`・`height`と各`variants`に記録します。長辺サイズや原本の寸法を、そのまま画像の幅として転記しないでください。
6. 暗部・粒子・色・細部が崩れていないか、実際の表示サイズで原寸画像と比較します。原本、選定入力・生成manifest、位置情報などの不要な個人情報をGitの対象に含めません。

2026-10-29の全画像差し替え依頼では、ユーザーが指定したフォルダのカラー20点・モノクロ20点、計40点を使用します。ICCはAdobe RGB 38点、ROMM RGB 1点、Display P3 1点です。閲覧コピーに元のICCを保持し、EXIF・GPS・XMPは移しません。元画像と公開範囲は[写真の出典と扱い](asset-sources.md)を参照してください。2026-10-26のInstagram由来40点は過去の掲載版であり、今回の提供画像とは区別します。

PillowのWebP対応がある既存のPython環境で、提供フォルダを指定して生成します。

```sh
python3 scripts/prepare-provided-assets.py --source-dir /path/to/originals
```

既定の選定入力は`artifacts/provided-selection.json`です。別ファイルを使う場合は`--selection /path/to/selection.json`を追加します。このスクリプトは画像の取得や公開を行わず、原寸画像を変更しません。指定したSHA-256と元ファイルの一致を確認し、各作品の閲覧サイズとサムネイルの合計を2MB未満に収めます。生成結果は`assets/photos/provided/`と、Git管理対象外の`artifacts/provided-image-manifest.json`です。

`data/works.js`は自動更新されません。生成manifestの`works`から表示用のパス・実寸・`variants`・提供元ファイル名とSHA-256を反映し、既存の`artist`と`collections`を保ちます。`source`は`type: 'provided'`、提供フォルダからの相対`file`、元ファイルの`sha256`を持つオブジェクトです。公開データに原寸画像の絶対パスを含めません。

原寸画像、選定入力、manifestはコミットしません。旧参照素材用の`npm run references`、`prepare-v1-assets.py`、`prepare-instagram-assets.py`は現在の提供40点の生成には使いません。画像を再生成しない通常の起動・表示確認は`npm run check`と`npm run dev`だけで行えます。

## 3. 作品データを更新する

`data/works.js`の`works`配列を編集します。各作品の`collection`でカラー／モノクロを分類し、同じコレクション内での配列順が掲載順になります。作家情報は`artist`、各作品群の名称・Instagram・目標枚数は`collections`にあります。

| 項目 | 扱い |
| --- | --- |
| `id` | 新しい作品には重複しない固定IDを付けます。既存作品の並べ替えでは変更しません |
| `collection` | `color`または`mono`。提供元の`color/`・`monochrome/`と対応させます |
| `src`・`thumbnail` | 写真全体とサムネイルの、実在する軽量画像パスを指定します |
| `width`・`height` | 表示用ファイルの実際の幅・高さを指定します |
| `variants` | `{ src, width, height }`の配列です。各WebPの実寸を記録し、幅の昇順に並べます |
| `alt` | 写っている内容を具体的に記述し、未確認の撮影地・年月・人物の事情を加えません |
| `source` | 提供画像は`{ type: 'provided', file, sha256 }`を保存します。`file`は所属フォルダから始まる相対名、`sha256`は元ファイルの64桁小文字16進数です。従来のInstagram投稿URL形式も検証できます |
| 掲載順 | 作品データの配列順で管理します |
| `title`・`caption` | 本人が確認した情報だけを追加します。未提供の内容は`null`のままにします |
| `selectionStatus` | 今回の公開選定は`approved`です。個別作品の本人承認を示す項目として使いません。`preview`は通常の公開検査で拒否します |

### 「日々について」を更新する

作家情報は同じファイルの`artist`を編集します。`name`、`designation`、`instagram`と活動履歴は本人の公開資料または本人が確認した情報に基づいて更新します。人物紹介をまとめたAIの回答だけを根拠に、居住地、性格、性別などを追加しません。

| 項目 | 更新時の扱い |
| --- | --- |
| `description` | 出典から確認できる撮影活動の紹介文。編集上の要約として扱い、本人の直接発言に見せません |
| `viewingNote` | サイトから鑑賞者への案内。作者による正式な作品解説や引用文とは区別します |
| `portrait` | `src`・実寸の`width`／`height`・見た目を伝える`alt`・公開元の`source`をセットで更新します。現在はlit.linkで配信されているWebPをそのまま保存した`assets/profile/hibi.webp`です |
| `essay` | 本人の文章へのリンクと案内文。記事の存在とリンク先を確認します |
| `activities` | 展示・写真集の名称、日付、会場、仕様を本人または主催者の一次資料で確認し、`href`を残します。価格や在庫など、掲載していない情報を推測で加えません |
| `links` | 作者紹介に表示する固定リンク。カラー／モノクロのInstagram、X、note、Storeをそれぞれ確認します |
| `statement` | 正式なステートメントが未提供のため`null`を維持します。紹介文や鑑賞案内から公式文を合成しません。削除済みの引用メッセージは再掲載の依頼があるまで戻しません |

プロフィール画像の差し替えでは、公開用の軽量コピーを`assets/profile/`に置き、元画像の構図・色を保ちます。人物の同一性や公開元を確認できない画像、生成した顔は使いません。出典、取得日、公開用ファイルの実寸・容量を[写真の出典と扱い](asset-sources.md)へ記録し、取得元ファイルや署名付き配信URLはコミットしません。作品の差し替えだけの場合、この作家情報とプロフィール画像を変更する必要はありません。

作者紹介の固定リンクと、コレクションに連動するフッターのInstagramリンクは用途が異なります。カラー／モノクロの切り替えで、作者紹介のリンク先を書き換えないでください。

現在の`targetCount`は両作品群とも20です。枚数を変更する依頼では目標枚数と実際のデータを同時に更新します。点数を満たすための複製や生成画像は加えません。

同じ作品を軽量画像へ差し替える場合は固定IDを保ちます。異なる作品への入れ替えでは新しいIDを使います。URLの`#collection=mono&photo=固定ID`や`#photo=固定ID`は作品を指すため、IDを別作品へ使い回しません。削除済みIDはURLの`collection`に指定した作品群の先頭へ移動し、指定がなければカラーの先頭へ移動します。今回の差し替え前の写真へのURLも確認します。

並べ替える際は、作品のデータ一式を移動します。IDだけ、画像パスだけを交換すると、直接リンクが別の写真を指す原因になります。

## 4. 自動検査する

プロジェクトのディレクトリで実行します。Node.jsが必要ですが、追加パッケージのインストールは不要です。

```sh
npm run check
```

固定IDの重複、画像パス、実寸、容量、必須ファイルに加え、各コレクションの実数と`targetCount`の一致を検査します。提供画像は`source`の所属フォルダ・相対名・SHA-256・重複を確認します。従来のInstagram URLではアカウント所属を確認します。各作品の閲覧サイズとサムネイルは同じ参照先を重複計上せず、合計2MB未満であることも検査します。`npm run check:preview`は試作用で、公開検査の代用にはしません。自動検査の成功だけでは見た目や操作の確認は完了しません。

## 5. ブラウザで確認する

```sh
npm run dev
```

<http://127.0.0.1:4186/> を開き、次を確認します。

- 最初の画面で作品が見え、初期表示の写真が意図したものになっている。
- 最初・途中・最後の写真と作品一覧のスクロール中に、ヘッダーが画面上部に表示される。PC・スマートフォン相当の画面で、写真や右側の位置ボタンと重ならず、「Gallery」と「About」を操作できる。
- カラー／モノクロ各20点の件数、配色、Instagramリンク、一覧の写真が連動する。
- 両作品群の途中から切り替えて戻ると、それぞれの鑑賞位置と一覧の位置へ復帰する。
- 写真・余白・ヘッダー・右側の閲覧位置ボタン・下部の切り替えボタン・フッターの全域で、マウスホイール・トラックパッド・スマートフォンの縦操作が一操作につき一枚の移動になる。
- ホイール・トラックパッドでは累積した縦の入力量に短い遅れで追従し、長い連続入力や慣性が残っていても一操作で一枚を超えて移動しない。入力が200ms以上途切れたら隣の停止位置へ収束する。
- 逆方向への新しい入力と、200ms以上入力を止めた後の次の操作を受け付け、収束の完了待ちで操作が失われない。途中で入力を加えたり方向を変えたりしても、現在の位置から連続して動く。
- スマートフォンでは一本指の縦ドラッグ中から一フレーム単位で指の位置に直接追従し、指を止めて保持すると途中位置を保つ。指を離す前に、自動で隣の写真へ移動しない。
- 一本指で触れてから離すまでを一操作とし、縦方向が優勢で36px以上動かしてから離すと隣の写真へ、短いドラッグなら元の写真へ戻る。ドラッグ後に操作ボタンが誤作動せず、通常のタップは機能する。
- 操作終了後は現在の位置・速度を引き継いで停止位置へ滑らかに収束し、固定時間の自動移動になっていない。OSの「動きを減らす」設定では追従を保ち、操作終了後の位置合わせを即座に行う。
- 最終作品の次に末尾メニューへ進み、逆方向の操作で最終作品へ戻れる。
- 一覧・ダイアログ内のスクロール、横方向の操作、複数指のピンチ、画面を拡大している間の移動はブラウザ標準の挙動を保つ。
- 掲載順が依頼どおりで、すべての画像が読み込まれる。
- 縦位置・横位置ともに写真全体が大きく表示され、画面の横中央に揃う。右側の閲覧位置ボタンと写真の間にも余白がある。暗部・明部・粒子、白枠・署名の見え方を提供された原寸画像と比較する。
- 前後の移動、一覧からの選択、作者紹介の開閉ができる。写真をクリックしても拡大画面は開かない。
- 作者紹介を両方の配色とスマートフォン相当の画面で開き、プロフィール画像・紹介文・活動履歴が読める。リンク先が正しく、Escapeや閉じるボタンで元の作品とフォーカスへ戻る。
- 一覧から選んだ作品へ移動し、該当作品の位置とフォーカスが分かる。
- 各写真のURLを再読み込みしても同じ作品が開く。ブラウザの戻る・進むも確認する。
- キーボードのTab、左右キー、Escapeで必要な操作ができ、閉じた後のフォーカスが分かる。
- スマートフォン相当の縦画面・横画面と大きな画面で、写真全体と操作が見える。
- 作品名・説明・プロフィール・外部リンクに未確認の情報が加わっていない。

確認用のスクリーンショットでは写真の全体、一覧、スマートフォン表示を残すと、差し替え前後を比較できます。

## 6. GitHubへ反映する

コードや作品データを更新した際は、`index.html`のCSS・JavaScript参照と`app.js`の作品データimportに付けた`v`のリリース識別子を同時に更新します。既存の閲覧者が古いモジュールを再利用する状態を避けるためです。現在の識別子は実際の参照行で確認します。

管理先は公開リポジトリ [bon214/hibi-portfolio](https://github.com/bon214/hibi-portfolio) です。更新時には対象の所有者・名称・公開範囲・接続を確認し、ローカル保存とGitHub反映を区別してください。

1. 変更一覧と差分を確認します。
2. 公開用閲覧コピー、作品データ、必要なコード・更新手順・出典記録・再生成スクリプトを対象にします。原寸画像、選定入力・生成manifest、旧試作コピー、QA用スクリーンショット、ローカルの`要件定義.md`、秘密情報は含めません。旧閲覧画像を削除する際は、どの作品・初期HTML・共有用画像からも参照されていないことを確認し、不要になった追跡済みファイルだけを対象にします。未追跡の複製ファイルを一括削除しません。新しい写真を追加する場合は、公開リポジトリへの保存を含む掲載範囲を確認します。
3. 更新依頼で指定された作品・順序・文章と一致していることを確認します。最初の写真を変更した場合は、`index.html`の初期画像・代替テキスト・作品ID・移動先と、`assets/share.jpg`・共有画像の説明も揃えます。未確認の本人承認や解説を記録しません。
4. 写真の追加・削除・並べ替え内容が分かるコミットを作り、対象リポジトリの`main`へpushします。
5. GitHub組込みのPages用Actionsが成功し、今回のコミットがデプロイされたことを確認します。
6. 公開ファイルの一致を検査し、公開URLのPC・スマートフォン表示と操作を確認します。

```sh
npm run verify:public -- https://bon214.github.io/hibi-portfolio/
```

検査はHTTP GETだけを行い、各ファイルのHTTP 200・Content-Type・SHA-256のローカル一致と、入口HTMLのcanonical・noindex・localhostを確認します。結果は`artifacts/public-verification.json`に保存され、全条件合格時だけ終了コード0になります。未反映ならデプロイ状態を確認し、反映後に再実行します。

初回のPages設定はSettings → Pages → Deploy from a branch → `main` → `/(root)`です。`.nojekyll`を維持します。branch公開に伴うGitHub組込みActionsを使い、独自workflowは追加しません。PublicリポジトリのPagesと標準runnerは無料対象です。有料サービス・有料runner・ドメイン購入は利用しません。[公開元設定](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)、[料金](https://docs.github.com/en/billing/concepts/product-billing/github-actions)

## 7. 戻す場合

変更前の画像と作品データを、Gitの変更履歴から同じ時点に戻します。共有した履歴を強制的に書き換えず、取り消す変更を新しい履歴として残す方法を基本にします。

戻した後も自動検査とブラウザ確認を行います。写真の削除やID変更を含む場合は、その作品への直接リンクを確認します。`main`へpushし、Pagesのデプロイ後に`npm run verify:public -- https://bon214.github.io/hibi-portfolio/`と公開画面を確認します。
