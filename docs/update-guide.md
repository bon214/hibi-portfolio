# 写真の更新ガイド

月1回程度、Codexへ写真の差し替え・並べ替えを依頼します。ローカル検査とブラウザ確認後、公開リポジトリ`bon214/hibi-portfolio`の`main`へpushし、GitHub Pagesのデプロイと公開ファイルを確認します。公開先URLは [https://bon214.github.io/hibi-portfolio/](https://bon214.github.io/hibi-portfolio/) です。

## 1. 更新依頼で渡すもの

- 追加・差し替えするWeb掲載用の画像。
- どの写真を残す・外す・差し替えるか。
- カラー／モノクロのどちらに掲載するか。現在は各20点です。
- 希望する掲載順。ファイル名または既存の固定IDで指定します。
- Instagramから選ぶ場合は、対象アカウントと投稿URL。告知画像と写真を区別します。
- 代替テキストに必要な、写真に写っている内容。
- 掲載する場合のみ、本人が確認したタイトル・撮影情報・短い言葉。

正式な作品名がない写真に作品名を作る必要はありません。代替テキストは画面を見ることが難しい人へ内容を伝えるための文章であり、作者の意図や写る人物の事情を推測する解説にはしません。

依頼例：

> カラーの3点を添付の写真A・B・Cへ差し替え、合計20点を維持してください。先頭は現在の `hibi-color-c3ka-2gvly8` のまま、A・B・Cをその次に並べます。モノクロの作品と順序は変えません。作品名と撮影地は掲載しません。まずローカルのプレビューで確認します。

## 2. 画像を準備する

1. ユーザーから指定された掲載範囲・作品・順序を確認します。各写真について別途本人承認を得たかどうかと、ユーザーによる公開選定指示を混同しません。
2. サイトで表示するWebP閲覧コピーとサムネイルを`assets/photos/instagram/`に置きます。長辺400・800・1400・2200pxを候補とし、取得元の長辺で止めます。拡大生成、切り取り、色調変更、回転はせず、作者の白枠・署名もそのまま保ちます。
3. 書き出した画像そのものの幅・高さを`width`・`height`と各`variants`に記録します。ファイル名の長辺サイズや原本の寸法を、そのまま画像の幅として転記しないでください。
4. 暗部・粒子・色・細部が崩れていないか、実際の表示サイズと拡大表示で比較します。
5. 原本、掲載を承認していない画像、位置情報などの不要な個人情報がGitの対象に混ざっていないか確認します。

2026-10-26の明示依頼に基づき、カラー[@hibigraph116](https://www.instagram.com/hibigraph116/)とモノクロ[@hibi_mono](https://www.instagram.com/hibi_mono/)から各20点を選定しました。取得JPEGは幅1440px・高さ1150〜1800pxで、撮影原本そのものではありません。全件に埋め込みICCはありません。現在の閲覧コピーは40点×4サイズとサムネイルの200 WebP、合計20,611,074 bytesです。初回カラー5点とモノクロの試作12点は現在の各20点へ置き換えました。取得元と公開範囲は [写真の出典と扱い](asset-sources.md) を参照してください。

取得JPEGは`assets/reference/instagram/`、選定入力は`artifacts/instagram-selection.json`に置き、Git管理対象外にします。選定入力は配列または`{"entries": [...]}`で、各項目に`id`・`collection`・`originalPath`・`source`・`alt`を指定します。`selectionStatus`は現在`approved`です。これはユーザーによる公開選定状態を表し、別途写真家本人の個別承認を取得したという意味ではありません。

PillowのWebP対応がある既存のPython環境で、まず書き込みなしの検査を行い、その後に生成します。

```sh
python3 scripts/prepare-instagram-assets.py --dry-run --expected-count 20 --require-selected
python3 scripts/prepare-instagram-assets.py --expected-count 20 --require-selected
```

このスクリプトは画像の取得や公開を行いません。取得JPEGを変更せず、閲覧用WebPと`artifacts/instagram-image-manifest.json`を生成します。EXIF/GPSはコピーせず、埋め込みICCがある画像ではそのICCを保持します。回転が必要なEXIF orientationは自動補正せず拒否します。

`data/works.js`は自動更新されません。生成manifestの作品レコードから表示用のパス・実寸・`variants`・投稿元などを反映し、既存の`artist`と`collections`を保ちます。manifestの元画像SHA-256を出典記録に残します。取得JPEG、選定入力、manifestはコミットしません。旧参照素材用の`npm run references`と`prepare-v1-assets.py`は現在の40点の生成には使いません。画像を再生成しない通常の起動・表示確認は`npm run check`と`npm run dev`だけで行えます。

## 3. 作品データを更新する

`data/works.js`の`works`配列を編集します。各作品の`collection`でカラー／モノクロを分類し、同じコレクション内での配列順が掲載順になります。作家情報は`artist`、各作品群の名称・Instagram・目標枚数は`collections`にあります。

| 項目 | 扱い |
| --- | --- |
| `id` | 新しい作品には重複しない固定IDを付けます。既存作品の並べ替えでは変更しません |
| `collection` | `color`または`mono`。所属アカウントと一致させます |
| `src`・`thumbnail` | 写真全体とサムネイルの、実在する軽量画像パスを指定します |
| `width`・`height` | 表示用ファイルの実際の幅・高さを指定します |
| `variants` | `{ src, width, height }`の配列です。各WebPの実寸を記録し、幅の昇順に並べます |
| `alt` | 写っている内容を具体的に記述し、未確認の撮影地・年月・人物の事情を加えません |
| `source` | その作品のInstagram投稿URLを保存します。カラーは`hibigraph116`、モノクロは`hibi_mono`の投稿です |
| 掲載順 | 作品データの配列順で管理します |
| `title`・`caption` | 本人が確認した情報だけを追加します。未提供の内容は`null`のままにします |
| `selectionStatus` | 今回の公開選定は`approved`です。個別作品の本人承認を示す項目として使いません。`preview`は通常の公開検査で拒否します |

### 「日々について」を更新する

作家情報は同じファイルの`artist`を編集します。`name`、`designation`、`instagram`と活動履歴は本人の公開資料または本人が確認した情報に基づいて更新します。人物紹介をまとめたAIの回答だけを根拠に、居住地、性格、性別などを追加しません。

| 項目 | 更新時の扱い |
| --- | --- |
| `description` | 出典から確認できる撮影活動の紹介文。編集上の要約として扱い、本人の直接発言に見せません |
| `philosophy`・`philosophySource` | 本人の言葉を原文と照合し、出典URLと一緒に更新します。編集文を引用に置き換えません |
| `viewingNote` | サイトから鑑賞者への案内。作者による正式な作品解説や引用文とは区別します |
| `portrait` | `src`・実寸の`width`／`height`・見た目を伝える`alt`・公開元の`source`をセットで更新します。現在はlit.linkで配信されているWebPをそのまま保存した`assets/profile/hibi.webp`です |
| `essay` | 本人の文章へのリンクと案内文。記事の存在とリンク先を確認します |
| `activities` | 展示・写真集の名称、日付、会場、仕様を本人または主催者の一次資料で確認し、`href`を残します。価格や在庫など、掲載していない情報を推測で加えません |
| `links` | 作者紹介に表示する固定リンク。カラー／モノクロのInstagram、X、note、Storeをそれぞれ確認します |
| `statement` | 正式なステートメントが未提供のため`null`を維持します。紹介文、引用、鑑賞案内から公式文を合成しません |

プロフィール画像の差し替えでは、公開用の軽量コピーを`assets/profile/`に置き、元画像の構図・色を保ちます。人物の同一性や公開元を確認できない画像、生成した顔は使いません。出典、取得日、公開用ファイルの実寸・容量を[写真の出典と扱い](asset-sources.md)へ記録し、取得元ファイルや署名付き配信URLはコミットしません。作品の差し替えだけの場合、この作家情報とプロフィール画像を変更する必要はありません。

作者紹介の固定リンクと、コレクションに連動するフッターのInstagramリンクは用途が異なります。カラー／モノクロの切り替えで、作者紹介のリンク先を書き換えないでください。

現在の`targetCount`は両作品群とも20です。枚数を変更する依頼では目標枚数と実際のデータを同時に更新します。点数を満たすための複製や生成画像は加えません。

同じ作品を軽量画像へ差し替える場合は固定IDを保ちます。異なる作品への入れ替えでは新しいIDを使います。URLの`#collection=mono&photo=固定ID`や`#photo=固定ID`は作品を指すため、IDを別作品へ使い回しません。初回カラー5点の削除済みIDは現在カラーの先頭へ移動します。削除時はこの移動先も確認します。

並べ替える際は、作品のデータ一式を移動します。IDだけ、画像パスだけを交換すると、直接リンクが別の写真を指す原因になります。

## 4. 自動検査する

プロジェクトのディレクトリで実行します。Node.jsが必要ですが、追加パッケージのインストールは不要です。

```sh
npm run check
```

固定IDの重複、画像パス、実寸、容量、必須ファイルに加え、各コレクションの実数と`targetCount`の一致、`source`のアカウント所属を検査します。現在は40作品・200画像の検査が成功しています。`npm run check:preview`は試作用で、公開検査の代用にはしません。自動検査の成功だけでは見た目や操作の確認は完了しません。

## 5. ブラウザで確認する

```sh
npm run dev
```

<http://127.0.0.1:4186/> を開き、次を確認します。

- 最初の画面で作品が見え、初期表示の写真が意図したものになっている。
- カラー／モノクロ各20点の件数、配色、Instagramリンク、一覧・拡大の写真が連動する。
- 両作品群の途中から切り替えて戻ると、それぞれの鑑賞位置と一覧の位置へ復帰する。
- 写真上・余白・操作部のどこからでも上下にスクロールでき、写真の位置に揃って止まる。連続入力が効かなくならず、末尾メニューにも進める。
- 掲載順が依頼どおりで、すべての画像が読み込まれる。
- 縦位置・横位置ともに元の構図が見える。暗部・明部・粒子、白枠・署名の見え方を取得JPEGと比較する。
- 前後の移動、一覧からの選択、拡大の開始と終了、作者紹介の開閉ができる。
- 作者紹介を両方の配色とスマートフォン相当の画面で開き、プロフィール画像・引用・紹介文・活動履歴が読める。リンク先が正しく、Escapeや閉じるボタンで元の作品とフォーカスへ戻る。
- 一覧から選んだ作品へスクロールし、拡大を閉じた後も該当作品の位置とフォーカスへ戻る。
- 各写真のURLを再読み込みしても同じ作品が開く。ブラウザの戻る・進むも確認する。
- キーボードのTab、左右キー、Escapeで必要な操作ができ、閉じた後のフォーカスが分かる。
- スマートフォン相当の縦画面・横画面と大きな画面で、写真全体と操作が見える。
- 作品名・説明・プロフィール・外部リンクに未確認の情報が加わっていない。

確認用のスクリーンショットでは写真の全体、一覧、拡大、スマートフォン表示を残すと、差し替え前後を比較できます。

## 6. GitHubへ反映する

コードや作品データを更新した際は、`index.html`のCSS・JavaScript参照と`app.js`の作品データimportに付けた`v`のリリース識別子を同時に更新します。既存の閲覧者が古いモジュールを再利用する状態を避けるためです。現在の識別子は実際の参照行で確認します。

管理先は公開リポジトリ [bon214/hibi-portfolio](https://github.com/bon214/hibi-portfolio) です。更新時には対象の所有者・名称・公開範囲・接続を確認し、ローカル保存とGitHub反映を区別してください。

1. 変更一覧と差分を確認します。
2. 公開用閲覧コピー、作品データ、必要なコード・更新手順・出典記録・再生成スクリプトを対象にします。取得JPEG、選定入力・生成manifest、旧試作コピー、QA用スクリーンショット、ローカルの`要件定義.md`、秘密情報は含めません。不要になった試作画像は、どの作品からも参照されていないことを確認して削除します。新しい写真を追加する場合は、公開リポジトリへの保存を含む掲載範囲を確認します。
3. 更新依頼で指定された作品・順序・文章と一致していることを確認します。未確認の本人承認や解説を記録しません。
4. 写真の追加・削除・並べ替え内容が分かるコミットを作り、対象リポジトリの`main`へpushします。
5. GitHub組込みのPages用Actionsが成功し、今回のコミットがデプロイされたことを確認します。
6. 公開ファイルの一致を検査し、公開URLのPC・スマートフォン表示と操作を確認します。

```sh
npm run verify:public -- https://bon214.github.io/hibi-portfolio/
```

検査はHTTP GETだけを行い、各ファイルのHTTP 200・Content-Type・SHA-256のローカル一致と、入口HTMLのcanonical・noindex・localhostを確認します。結果は`artifacts/public-verification.json`に保存され、全条件合格時だけ終了コード0になります。未反映ならデプロイ状態を確認し、反映後に再実行します。

初回のPages設定はSettings → Pages → Deploy from a branch → `main` → `/(root)`です。`.nojekyll`を維持します。branch公開に伴うGitHub組込みActionsを使い、独自workflowは追加しません。PublicリポジトリのPagesと標準runnerは無料対象です。有料サービス・有料runner・ドメイン購入は利用しません。[公開元設定](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)、[料金](https://docs.github.com/en/billing/concepts/product-billing/github-actions)

## 7. 戻す場合

変更前の画像と作品データを、Gitの変更履歴から同じ時点に戻します。共有した履歴を強制的に書き換えず、取り消す変更を新しい履歴として残す方法を基本にします。

戻した後も自動検査とブラウザ確認を行います。写真の削除やID変更を含む場合は、その作品への直接リンクを確認します。`main`へpushし、Pagesのデプロイ後に`npm run verify:public -- https://bon214.github.io/hibi-portfolio/`と公開画面を確認します。
